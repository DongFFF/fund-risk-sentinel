# 01 · 需求与课题背景

> 本文说明「为什么要做这套系统」，以及它对应的课题研究主线。
> 读代码前先读这篇，能理解很多设计取舍的来由。

---

## 一、现实痛点

高校科研经费管理长期依赖「事后审计 + 人工抽查」，在经费规模增长、制度体系复杂的双重压力下，暴露出三个结构性痛点：

| 痛点 | 具体表现 | 后果 |
| --- | --- | --- |
| **发现滞后** | 违规线索往往在结题审计、专项检查时才暴露 | 资金已支出，追回成本高，整改被动 |
| **制度规则分散** | 国家办法、负面清单、校级细则、院系口径并存，表述不一致 | 同一笔业务在不同口径下判断不同，经办人无所适从 |
| **材料核验成本高** | 报销单、合同、发票、审批意见多为非结构化文本，靠人逐份比对 | 抽查覆盖率低，大量业务实质上是"形式审核" |

**共性症结**：制度是文本，材料也是文本，两者之间的"关联判断"只能靠人的经验完成。经验不可复制、不可追溯、不可批量执行。

---

## 二、课题研究主线

本课题的核心命题是：**轻量化大模型能否在高校科研经费这一垂直场景中，承担"制度—材料"关联判断的工作，并把判断过程做成可核验、可追溯的线索？**

围绕这一命题，课题提出**三类核心能力**：

### 能力① 材料理解与结构化抽取

从非结构化材料中识别关键要素：项目、科目、金额、时间、供应商、审批角色；并判断附件齐全性与字段间一致性。

- 落点：`src/fund_risk_sentinel/ingest/` + `extract/`
- 关键要求：**字段级可核验**——每个抽取值都要能回溯到材料中的具体位置

### 能力② 制度语义匹配与风险推理

把材料事实与制度条款、校内口径关联起来，识别科目不匹配、用途模糊、额度或时点异常、合同与申请信息不一致、跨材料语义矛盾等情形。

- 落点：`src/fund_risk_sentinel/rules/` + `review/`
- 关键要求：**命中即可回溯条款**——不允许出现"模型觉得有问题但说不出依据"的线索

### 能力③ 结果解释与证据定位

输出风险等级、命中依据、关联材料、建议复核点，使审核人能够独立判断该线索是否成立。

- 落点：`src/fund_risk_sentinel/explain/`
- 关键要求：**可解释性优先于召回率**——宁可少报，不可误导

## 三、五元关联框架

三类能力共同服务于一个数据组织方式——「事项—规则—证据—风险—处置」五元关联：

```
事项(Event) ── 规则(Rule) ── 证据(Evidence) ── 风险(Risk) ── 处置(Disposition)
  预算/合同/     额度/用途/     申请单/合同/     缺失/冲突/      补充/退回/
  报销/结算      程序/时点/     发票/审批意见   偏离/越权/      限制/会商/
                 授权                           异常组合        放行留痕
```

这个框架的作用是**把一次审查拆成可分别验证的五段**：

- 事项是否识别正确？（`EventType`）
- 规则是否适用、条件是否成立？（`Rule` / `RuleHit`）
- 证据能否定位到材料？（`Evidence`）
- 风险类别与等级是否恰当？（`RiskFinding`）
- 处置建议是否与风险匹配？（`Disposition`）

任何一段出错，都能被单独发现和修正，而不是笼统地"模型判断错了"。

## 四、定位边界（重要）

**本系统输出的是「待核验线索」，不是合规结论。**

这一边界不是免责声明，而是设计前提，体现在代码中：

| 设计 | 代码体现 |
| --- | --- |
| 不叫"结论"叫"线索" | 领域模型命名为 `RiskFinding` 而非 `RiskConclusion` |
| 默认必须人工复核 | `RiskFinding.needs_human_review` 默认 `True`，无开关可关 |
| 禁止定性表述 | `prompts/common.py` 的 `GOVERNANCE_GUARDRAIL` 明确禁止"违规""合规"等措辞 |
| 证据不足必须显式标注 | 证据不足时 `level` 取 `UNKNOWN`，不允许默认降级为"低风险" |
| 结论附带免责声明 | `ReviewConclusion.disclaimer` 默认文案随每条结论输出 |

复核判断、授权处置、例外认定，始终由具有相应权限的人员承担。

## 五、技术路线选择

课题提出**四条适配路径**，本系统按"能用简单方案解决就不上复杂方案"的原则落地：

| 路径 | 适用场景 | 本系统落点 | 说明 |
| --- | --- | --- | --- |
| 结构化规则 + 知识检索 | 制度口径清晰稳定 | `rules/engine.py`、`rules/knowledge_base.py` | 确定性最高，断网可用 |
| 检索增强生成（RAG） | 需制度依据支撑 | 知识库检索 → 注入提示模板 | 用 BM25 替代向量库，避免 exe 依赖模型下载 |
| 提示模板与指令工程 | 需快速验证能力边界 | `prompts/` | 治理约束集中在此 |
| 参数高效微调（LoRA/QLoRA） | 需领域术语与情境适配 | `llm/` 指向本地微调端点 | 预留接口，不强制 |

**三条能力链路各自独立、可单独替换**：换掉模型不影响规则引擎；换掉规则库不影响抽取。

## 六、现实约束与应对

| 约束 | 应对 |
| --- | --- |
| **尚无标准化标注数据** | 全部数据先经大模型审查，逐步沉淀为标注语料；系统先跑通流程，指标只作趋势参考 |
| **材料含个人敏感信息** | 上传即脱敏（身份证/手机/银行卡/邮箱），保形替换保留长度与首尾特征 |
| **不能依赖联网** | 内置离线模拟模型，全链路可断网自检；检索用字符二元组 BM25，零额外依赖 |
| **使用者不一定是技术人员** | 桌面 exe，双击即用；模型接入走界面配置，不写代码 |
| **审计要求可追溯** | 哈希链审计日志，任何篡改都能被定位 |

```
  └─ 三类核心能力
       ├─ ① 材料理解与结构化抽取  →  ingest/ extract/
       ├─ ② 制度语义匹配与风险推理 →  rules/ review/
       └─ ③ 结果解释与证据定位    →  explain/

                      └─ 交付形态：桌面 exe → ui/ app.py
```
