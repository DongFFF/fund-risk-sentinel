# 02 · 系统架构

> 本文说明代码怎么组织、数据怎么流动、以及为什么这样分层。

## 一、分层总览

```
┌─────────────────────────────────────────────────────────────┐
│  ui/            PySide6 桌面界面（7 个页面）                  │
│  只负责"呈现与收集"，全部判断逻辑在业务层                      │
└───────────────────────────┬─────────────────────────────────┘
                            │ AppContext（配置/客户端/流水线/存储）
┌───────────────────────────▼─────────────────────────────────┐
│  review/        审查主流程编排（6 阶段流水线）                 │
│   assemble → extract → rule_check → retrieve → reason → explain
└──┬────────┬─────────┬──────────┬──────────┬─────────────────┘
   │        │         │          │          │
┌──▼───┐ ┌──▼────┐ ┌──▼─────┐ ┌──▼──────┐ ┌─▼────────┐

│材料解析│ │结构化 │ │规则+知识│ │解释与   │ │模型统一  │
│       │ │抽取   │ │检索    │ │证据定位 │ │接入      │
└──────┘ └───────┘ └────────┘ └─────────┘ └──────────┘
                            │
        ┌───────────────────┴───────────────────┐
   ┌────▼─────┐                        ┌────────▼────────┐
   │storage/  │                        │ evaluate/       │
   │SQLite+审计│                        │ 六维指标        │
   └──────────┘                        └─────────────────┘
        └────────────────┬────────────────────┘
                    ┌────▼─────┐

                    │ config/  │  配置加载与路径解析

```

**依赖方向严格单向**：`core` / `config` 不依赖任何上层；`ui` 依赖一切，但不被任何模块依赖。因此整套业务逻辑可以脱离界面做自动化测试（`tests/` 就是这么做的）。

## 二、审查流水线的六个阶段

`ReviewPipeline._run_core()` 按固定顺序执行，每个阶段都产出 `PipelineStageRecord`（状态、耗时、token 用量、降级说明）：

| # | 阶段 | 做什么 | 降级行为 |
| --- | --- | --- | --- |
| 1 | `assemble` | 按角色排序装配材料上下文（制度优先），超预算截断并**明确标注** | 无 |
| 2 | `extract` | 规则抽取 + 模型抽取 → 交叉校验合并 | 模型不可用 → 只用规则抽取 |
| 3 | `rule_check` | 规则引擎求值，产出 `RuleHit` | 规则库为空 → 跳过并记 warning |
| 4 | `retrieve` | 制度知识库 BM25 检索，取相关条款 | 知识库为空 → 跳过 |
| 5 | `reason` | 规则线索 + 模型线索 → 合并去重 → `RiskFinding` | 模型不可用 → 只用规则线索 |
| 6 | `explain` | 生成摘要、逐条解释、可追溯说明 | 模型不可用 → 确定性摘要 |

**关键设计：降级不等于失败。**

- 单阶段失败 → 记 `StageStatus.DEGRADED`，写进 `conclusion.degraded_stages`
- 用户会在结论中看到"本次结果部分来自降级路径"，而不是被蒙在鼓里
- 只有"材料全部无法解析"才判 `ReviewStatus.FAILED`

## 三、模型接入层：可插拔设计

```
                    ┌──────────────────────┐
                    │  BaseLLMProvider     │  ← 抽象基类
                    │  complete() 抽象      │
                    │  chat() / chat_json() │
                    │  health_check()       │
                    └──────────┬───────────┘
                               │
   ┌───────────────┬───────────┼───────────┬──────────────┐
   ▼               ▼           ▼           ▼              ▼
OpenAI兼容      Anthropic    Gemini      Mock        （用户自定义）
DeepSeek/通义     Claude      Gemini    离线自检     继承后注册
Kimi/智谱
Ollama/vLLM
```

**为什么用 OpenAI 兼容协议做主力？** 因为 DeepSeek、通义千问、Kimi、智谱、Ollama、vLLM、LM Studio 都提供 `/chat/completions` 接口。一家适配器覆盖绝大多数厂商，"可调用任何模型 API"这句承诺才落地。

```python
# 接入一个从未见过的新厂商，只需在 providers.yaml 加几行：
my_provider:
  type: openai_compatible
  base_url: https://api.example.com/v1
  api_key: ${MY_API_KEY}
  model: example-model
```

`LLMClient` 负责：

- **回退链**：主 provider 失败 → 按 `fallback` 列表依次尝试
- **用量累计**：prompt/completion token、估算成本
- **调用留痕**：每次调用记 `CallRecord`（provider/model/task/耗时/token/是否降级/错误）
- **降级标记**：`last_degraded` 供上层写进结论

## 四、材料解析层：注册表 + 加载器

```
LoaderRegistry
  ├─ TextLoader      .txt
  ├─ MarkdownLoader  .md
  ├─ CsvLoader       .csv  （Sniffer 自动判分隔符）
  ├─ JsonLoader      .json （list[dict] → 表格）
  ├─ DocxLoader      .docx （按文档流遍历段落+表格）
  ├─ XlsxLoader      .xlsx （read_only + data_only）
  ├─ PdfLoader       .pdf  （pypdf → PyMuPDF → OCR 三级）
  └─ ImageLoader     .png/.jpg （OCR 或 多模态）
```

四个上传接口（都返回统一的 `IngestResult`）：

| 接口 | 场景 |
| --- | --- |
| `load_paths(paths)` | 选文件 |
| `load_folder(dir)` | 选文件夹 |
| `load_bytes(name, data)` | 浏览器/接口上传内存流 |
| `load_text(text, name=)` | 手工粘贴 |

**健壮性设计**：

- 单文件解析失败 → 逐条记 error，**不中断整批**
- 内容指纹（sha256）去重，同一份材料传两次只算一次
- PDF 解析不出文字（扫描件）→ 打 `needs_ocr` 标，而非静默通过
- 编码探测：utf-8-sig / utf-8 / gb18030 / gbk / big5 / utf-16 / latin-1

## 五、规则引擎：安全表达式沙箱

规则条件写成表达式（如 `amount > budget_amount and has_invoice`），由 AST 白名单沙箱求值：

- **允许**：比较、布尔运算、算术、`fields.get(...)` 只读调用
- **禁止**：`__import__`、属性穿透（`().__class__.__bases__`）、列表推导、lambda、`open`
- **白名单函数**：`abs/min/max/len/round/int/float/str/bool/sum/any/all/to_number/is_empty/contains_any/contains_all/regex_match/days_between`

不用 `eval()` 的原因：规则文件是可编辑的（校内可自行加规则），一旦用了 `eval`，一个规则文件就等于一个任意代码执行入口。

`build_facts()` 把抽取结果与材料集合整理成规则可用的变量字典，并自动推算派生值（如 `days_after_event` 由业务日期与办理日期计算）。

## 六、检索层：为什么不用向量库

制度条款检索用**字符二元组 + BM25**，而不是向量数据库：

| 方案 | 优点 | 本场景的问题 |
| --- | --- | --- |
| 向量库（如 ChromaDB） | 语义召回强 | 需随包分发嵌入模型（数百 MB）、首次运行要下载、断网不可用 |
| **BM25（本系统）** | 零依赖、断网可用、可解释（能看命中词） | 语义泛化弱，靠同义词与条款切分弥补 |

对"制度条款检索"这个任务，**可解释性比语义泛化更重要**——审核人需要知道"为什么这条条款被召回"，而不是接受一个相似度分数。BM25 能直接展示命中的词。

参数：`k1=1.5`、`b=0.75`（标准取值）。

## 七、存储与审计

```
sentinel.db (SQLite, WAL 模式)
  ├─ tasks          审查任务
  ├─ materials      材料元信息（不存正文，正文在文件系统）
  ├─ conclusions    结论（payload_json 全量 + 分表冗余）
  ├─ findings       风险线索（便于按等级/状态查询）
  ├─ dispositions   处置记录
  ├─ audit_log      审计日志（哈希链）
  ├─ evaluations    评测报告
  └─ meta           架构版本等元信息
```

**审计日志哈希链**：

```
entry_hash = sha256(prev_hash + ts + level + action + actor + target + detail_json)
```

- 每条记录都引用前一条的哈希，改任何一条都会导致后续全部校验失败
- `verify_chain()` 能定位到**具体第几条**被改
- 双写：SQLite（可查询）+ 按日文本日志（可人工翻阅）
- 写日志前递归清理 `api_key`/`token`/`password` 等字段

**WAL + 线程局部连接**：支撑"后台线程跑审查"与"界面线程读列表"并行，互不阻塞。

## 八、打包与路径

`config/paths.py` 统一处理两种运行形态：

| | 源码运行 | 打包后（`sys.frozen`） |
| --- | --- | --- |
| 项目根 | `<repo>/` | exe 所在目录 |
| 只读资源 | `<repo>/` | `sys._MEIPASS`（解压临时目录） |
| 可写配置 | `<repo>/config/` | `%APPDATA%/FundRiskSentinel/config/` |
| 可写数据 | `<repo>/data/` | `%LOCALAPPDATA%/FundRiskSentinel/` |

**为什么可写目录必须换到用户目录？** PyInstaller 单文件模式解压出的临时目录是只读的，写配置会直接失败。这也是很多"打包后能启动但保存不了"问题的根因。

配置搜索顺序（后者补前者）：环境变量 `FUND_RISK_CONFIG_DIR` → 用户配置目录 → 项目 `config/` → 打包资源内 `config/`。

## 九、错误处理约定

| 层级 | 策略 |
| --- | --- |
| 单文件解析 | 记 error，继续处理其余文件 |
| 单阶段失败 | 降级 + 记 `degraded_stages`，继续后续阶段 |
| 模型调用失败 | 按回退链重试 → 全失败则降级为规则结果 |
| 规则条件非法 | 加载时跳过该条 + 记 warning，不让整个规则库崩掉 |
| 配置缺失 | 用内置默认值，界面提示"配置待处理 N 项" |
| 未捕获异常 | 全局 hook → 弹窗告知 + 写日志，而非静默崩溃 |

原则：**任何单点故障都不应让用户拿不到结果，但任何降级都必须让用户知道。**
