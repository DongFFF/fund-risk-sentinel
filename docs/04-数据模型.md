# 04 · 数据模型

> 本文说明领域模型怎么设计，以及每个字段为什么存在。
> 全部定义在 `src/fund_risk_sentinel/core/models.py`，枚举在 `core/enums.py`。

## 一、五元框架的模型映射

```
事项(Event)      →  ReviewTask / EventType
规则(Rule)       →  Rule / RuleHit
证据(Evidence)   →  Material / Evidence
风险(Risk)       →  RiskFinding
处置(Disposition)→  Disposition
```

---

## 二、枚举体系

所有枚举继承 `StrEnum`（`str` 子类），因此可直接参与 JSON 序列化、YAML 配置与 SQLite 存储，无需转换。中文标签统一放在 `*_LABELS` 映射中供界面复用。

```python
class StrEnum(str, Enum):
    @classmethod
    def values(cls) -> list[str]: ...
    @classmethod
    def from_value(cls, value, default=None): ...
        # 宽松解析：接受枚举成员 / 值字符串 / 成员名 / 中文标签
```

| 枚举 | 取值 |
| --- | --- |
| `EventType` | `budget` `advance` `reimbursement` `contract` `procurement` `transfer` `settlement` `other` |
| `RuleDimension` | `amount` `purpose` `procedure` `timing` `authority` |
| `RiskCategory` | `missing` `conflict` `deviation` `override` `anomaly` |
| `RiskLevel` | `unknown` `low` `medium` `high`（另有 `RISK_LEVEL_WEIGHT` 排序权重） |
| `EvidenceStatus` | `present` `missing` `unclear` `conflicting` |
| `DispositionType` | `supplement` `return` `restrict` `consult` `adjust_budget` `release_recorded` `pending_review` |
| `DocumentRole` | `policy` `application` `contract` `invoice` `approval` `acceptance` `budget` `other` |
| `DocumentFormat` | `txt` `md` `csv` `json` `docx` `xlsx` `pdf` `image` `unknown` |
| `ReviewStatus` | `pending` `running` `completed` `needs_human` `failed` |
| `HumanVerdict` | `pending` `accepted` `partial` `rejected` `missed` |
| `MetricDimension` | `accuracy` `recall` `latency` `consistency` `explainability` `adoption` |
| `StageStatus` | `pending` `running` `ok` `skipped` `degraded` `failed` |
| `Capability` | 三类核心能力 |
| `AdaptationPath` | `rule_rag` `rag` `prompt` `peft` |

## 三、核心模型

### 3.1 Material —— 一份材料

```python
class Material(Base):
    material_id: str          # mat_xxx
    filename: str             # 原始文件名
    path: str                 # 本机绝对路径（不随材料外发）
    fmt: DocumentFormat
    role: DocumentRole        # 在证据链中的角色
    size_bytes: int
    sha256: str               # 内容指纹，用于去重与完整性校验
    uploaded_at: datetime
    page_count: int
    text: str                 # 提取出的纯文本正文（有长度上限）
    tables: list[list[list[str]]]   # tables[表序号][行][列]
    metadata: dict            # 解析器补充的元信息
    redaction_applied: bool
    redaction_log: list[str]  # 脱敏动作记录
    source: str               # local_upload / api / folder_scan / manual
    retention_until: str      # 保存期限 YYYY-MM-DD

    @property
    def char_count(self) -> int: ...
```

**为什么存 `sha256`？** 两个用途：① 去重——同一份材料传两次只算一次；② 完整性——事后能验证"审查用的材料有没有被换过"。

**为什么 `path` 不随材料外发？** 材料元信息可能进入提示词，本机路径属于不必要的泄露面。

### 3.2 ExtractedField / ExtractedFields —— 能力① 产出

```python
class ExtractedField(Base):
    name: str                 # amount / budget_subject / supplier ...
    value: str                # 规范化后的值
    raw: str                  # 材料中的原始表述
    confidence: float         # 0~1
    source_material_id: str   # 该字段来自哪份材料
    locator: str              # 定位：p.3 / 表1第4行 / 单元格D7

class ExtractedFields(Base):
    fields: dict[str, ExtractedField]
    attachments_expected: list[str]   # 制度要求的附件清单
    attachments_present: list[str]    # 实际提供的附件
    consistency_issues: list[str]     # 字段间一致性疑点
    notes: list[str]
    produced_by: str          # llm / rule / hybrid
    provider: str
    model: str
```

**每个字段都带 `raw` + `locator` + `confidence`**：审核人能看到"模型从哪句话读出这个值""它有多确定"。这是"字段级可核验"的落地方式——不给黑盒数字。

`produced_by` 记录产出方式，使"哪些是规则抽取、哪些是模型抽取"可分辨。

### 3.3 Rule / RuleHit —— 规则与命中

```python
class Rule(Base):
    rule_id: str              # AMT-001（唯一）
    name: str
    dimension: RuleDimension
    event_types: list[EventType]      # 适用的事项类型
    condition: str                    # 表达式，沙箱求值
    requirement: str                  # 制度要求原文
    risk_category: RiskCategory
    level_hint: RiskLevel
    disposition_hint: DispositionType
    suggestion: str
    basis: list[ClauseRef]            # 制度依据
    enabled: bool
    source: str                       # builtin / institution / custom
    version: str

class RuleHit(Base):
    rule_id: str
    rule_name: str
    dimension: RuleDimension
    requirement: str
    risk_category: RiskCategory
    level_hint: RiskLevel
    disposition_hint: DispositionType
    suggestion: str
    matched_expression: str           # 命中的条件表达式原文
    evaluated_values: dict            # 参与求值的变量快照
```

**`RuleHit` 为什么快照 `evaluated_values`？** 事后复盘时，规则库可能已改版。留存当时的变量快照，才能回答"当时为什么命中"。

**`level_hint` 而非 `level`**：规则给的是"提示等级"，最终等级由推理阶段结合证据综合判定。

### 3.4 Evidence —— 证据定位

```python
class Evidence(Base):
    evidence_id: str
    material_id: str
    material_name: str
    role: DocumentRole
    status: EvidenceStatus
    locator: str              # 页码 / 表格 / 单元格
    snippet: str              # 原文摘录，供审核人快速核对
    supports: bool            # 该证据是支持还是反驳本线索
```

**`supports` 字段的意义**：线索不仅要列"支持证据"，也要能列"反驳证据"。只列支持证据的线索本质上是有偏的。

### 3.5 RiskFinding —— 风险线索（能力②③ 产出）

```python
class RiskFinding(Base):
    finding_id: str           # risk_xxx
    title: str
    category: RiskCategory
    level: RiskLevel
    confidence: float
    description: str
    rationale: str            # 推理过程：制度怎么要求 → 材料显示什么 → 差异在哪
    matched_clauses: list[ClauseRef]   # 命中的制度条款
    rule_hits: list[RuleHit]           # 命中的规则
    evidences: list[Evidence]          # 证据定位
    counter_evidence: list[str]        # 不确定点 / 反向证据
    suggested_disposition: DispositionType
    needs_human_review: bool = True    # 默认 True，不可关闭
    human_verdict: HumanVerdict
    human_note: str
    reviewed_by: str
    reviewed_at: datetime | None
```

**命名是 `RiskFinding` 而不是 `RiskConclusion`。** 这不是文字游戏——命名会塑造使用者的心理预期。叫"结论"，人会倾向于接受；叫"线索"，人会倾向于核实。

**`needs_human_review` 默认 `True` 且无开关可关。** 这是硬性治理边界，不是可配置项。

**`counter_evidence` 必须能填。** 允许模型说"这条线索有什么不确定性"，比强制它给一个干净结论更有价值。

### 3.6 Disposition —— 处置

```python
class Disposition(Base):
    disposition_id: str
    finding_id: str
    type: DispositionType
    note: str
    decided_by: str
    decided_at: datetime
    follow_up: str            # 后续跟踪要求
```

处置是**人工动作的记录**，系统只提供建议（`suggested_disposition`），不代替人做决定。

### 3.7 ReviewConclusion —— 结论

```python
class ReviewConclusion(Base):
    conclusion_id: str        # ccl_xxx
    task_id: str              # 关联任务（可追溯底线）
    status: ReviewStatus
    event_type: EventType
    findings: list[RiskFinding]
    summary: str              # 客观陈述，不下合规判断
    overall_level: RiskLevel
    recommended_actions: list[DispositionType]
    statistics: dict[str, int]        # 各级别线索计数
    extracted: ExtractedFields | None
    pipeline_trace: list[PipelineStageRecord]
    usage: TokenUsage
    generated_at: datetime
    duration_ms: int
    provider: str
    model: str
    adaptation_paths: list[AdaptationPath]
    degraded_stages: list[str]        # 发生降级的阶段，需向用户明示
    disclaimer: str                   # 默认文案随每条结论输出

    def add_finding(self, finding) -> None: ...
    def recount(self) -> "ReviewConclusion": ...   # 重算统计与总体等级
```

**`degraded_stages` 为什么必须存在？** 如果模型挂了、退回纯规则结果，使用者有权知道。悄悄降级是最危险的行为——结果看起来一样，可信度却完全不同。

**`disclaimer` 随结论输出**：界面上、Markdown 底稿里、导出的文件里都会带上。

### 3.8 PipelineStageRecord —— 阶段轨迹

```python
class PipelineStageRecord(Base):
    stage: str                # assemble / extract / rule_check / retrieve / reason / explain
    title: str
    status: StageStatus
    message: str
    started_at: datetime
    duration_ms: int
    provider: str
    model: str
    prompt_tokens: int
    completion_tokens: int
```

**为什么要记录每个阶段？** 出了问题要能定位到"是抽取错了，还是规则写错了，还是模型推理错了"。没有阶段轨迹，只能笼统地说"模型不行"。

### 3.9 TokenUsage —— 用量与成本

```python
class TokenUsage(Base):
    prompt_tokens: int
    completion_tokens: int
    total_calls: int
    estimated_cost: float
    @property
    def total_tokens(self) -> int: ...
```

## 五、存储表结构

```
tasks          审查任务（含 material_count / finding_count / high_count / overall_level 冗余列）
materials      材料元信息（不存正文）
conclusions    结论（payload_json 全量 + 分表冗余）
findings       风险线索（便于按等级/状态/任务查询）
dispositions   处置记录
audit_log      审计日志（prev_hash / entry_hash 哈希链）
evaluations    评测报告
meta           架构版本等元信息
```

**为什么结论既存 `payload_json` 又拆 `findings` 分表？** 全量 JSON 保证"读回来跟写进去一模一样"，分表保证"能按等级/状态高效查询与统计"。二者互为校验：分表数量与 JSON 里不一致，就说明写库出了问题。
