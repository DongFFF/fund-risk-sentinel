# 07 · 开发路线图

> 本文说明"已经做到哪、接下来做什么、怎么判断做到了"。

---

## 一、总体思路

```
先把流程跑通  →  再用真实材料验证  →  再沉淀标注数据  →  再做领域适配
（当前阶段）      （下一步）            （并行推进）        （后期）
```

**为什么是这个顺序？** 在还没有标准化标注数据的时候，直接去调模型、做微调，没有基准可比，等于盲调。先把"上传 → 抽取 → 规则 → 推理 → 解释 → 落库 → 审计"这条链路完整跑通，让数据开始积累，后面的每一步才有依据。

## 三、近期（v0.2.x）—— 用真实材料验证

**目标**：拿真实业务材料跑通，暴露问题。

| 任务 | 验收标准 |
| --- | --- |
| 收集 20~50 组脱敏后的真实材料 | 覆盖报销、合同、采购、结算等事项类型 |
| 用真实模型跑通全链路 | 无解析失败、无流程中断 |
| 逐条人工复核并记录 | 每条线索标采纳/部分采纳/否决/漏报 |
| 修正规则库 | 误报集中在哪条规则就改哪条 |
| 收紧提示词 | 针对模型实际输出的问题调整 `prompts/` |

**产出**：第一份真实数据的六维指标基线（仅作趋势参考）。

---

## 四、中期（v0.3.x）—— 沉淀标注数据

**目标**：把人工复核结果转化为可复用的基准数据。

| 任务 | 说明 |
| --- | --- |
| 复核结果结构化导出 | 已有：`HumanVerdict` 落库 |
| 构建评测基准集 | 材料 + 人工认定的"应报线索"清单 |
| 建立回归测试 | 规则或提示词改动后，自动比对基线 |
| 指标从"趋势参考"升级为"能力结论" | 样本量达到可判断水平（建议 ≥ 100 组） |

**关键**：这一步没有捷径。标注数据只能靠真实复核积累，这也是系统从"能跑"到"可信"的必经之路。

---

## 五、后期（v0.4+）—— 领域适配

按课题提出的四条适配路径，逐级递进：

| 路径 | 什么时候上 | 判据 |
| --- | --- | --- |
| 结构化规则 + 知识检索 | **已上线** | 制度口径清晰稳定的部分 |
| RAG | **已上线**（BM25） | 需要制度依据支撑的场景 |
| 提示模板与指令工程 | **已上线** | 持续迭代 |
| 参数高效微调（LoRA/QLoRA） | 提示词优化收益见顶时 | 通用模型在领域术语/情境判断上反复出错，且错误模式稳定 |

**为什么微调排最后？** 微调成本高、迭代慢、可解释性下降。只有当"提示词怎么改都改不好"且"错误模式稳定可归纳"时，微调才是正确选择。接口已预留（`llm/` 指向本地端点 + `adaptation_path: peft` 标注）。

### 其他后期方向

| 方向 | 说明 |
| --- | --- |
| 语义检索增强 | 可选引入向量检索，与 BM25 融合；需权衡 exe 体积与离线可用性 |
| 跨材料关联分析 | 同一供应商短期多笔、拆分报销等组合异常（部分已实现） |
| 制度版本管理 | 条款生效日期与版本追溯 |
| 批量审查 | 文件夹批量处理 + 汇总报告 |
| 与校内系统对接 | 提供 HTTP 接口，对接报销系统 |

## 六、明确不做的事

| 不做 | 原因 |
| --- | --- |
| 自动作出合规认定 | 责任边界，见 `docs/06-安全与合规.md` |
| 自动执行处置动作 | 处置权在审批人 |
| 评价学术价值/绩效 | 超出系统能力范围，且易造成误伤 |
| 上传任何数据到自有服务器 | 数据不出本地 |
| 依赖联网才能启动 | 断网可用是硬性要求 |
| 强制依赖向量库 | exe 体积与离线可用性优先 |

## 八、怎么判断"做到了"

| 阶段 | 判据 |
| --- | --- |
| 流程跑通 | 上传任意支持格式的材料，都能拿到带依据的线索（**已达成**） |
| 真实可用 | 审核人愿意用它的结果做参考，而不是走个形式 |
| 可信 | 六维指标在足够样本下稳定达标 |
| 可推广 | 换一所学校，改规则库和知识库即可上线，不用改代码 |

**最终标准不是指标多好看，而是：审核人用了一段时间后，觉得"没有它不踏实"。**
